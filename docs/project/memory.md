# Persistent Project Memory: AegisPay AI

## 1. Confirmed Decisions

- **Architecture**: Modular Monolith. All core domains (transactions, risk engine, investigation orchestration) exist within a single deployable backend package with strict internal boundaries.
- **Backend Tech Stack**:
  - Python 3.14 (fully verified compatible with required dependencies).
  - FastAPI + Uvicorn for asynchronous REST API.
  - Pydantic v2 + `pydantic-settings` for typed configuration and request validation.
  - SQLAlchemy 2.x asynchronous ORM with `psycopg` (v3) async driver (`postgresql+psycopg://`).
  - Alembic for database migrations.
  - `uv` for dependency and virtual environment management.
  - Ruff (linting & formatting) and mypy (typechecking).
  - pytest + pytest-asyncio + HTTPX for testing.
- **Frontend UI Prototype Preservation & Reuse**:
  - Inspected `Intent-Check-Fintech-Prototype.zip` supplied by developer.
  - Identified `artifacts/intent-check` as the exact source matching the supplied screenshot (`Aster Bank` / Live payment console with 6-metric summary strip, bank-wide payment activity queue, and interactive customer Android device preview simulator).
  - Preserved the full interactive design, mobile simulator (with voice and chat simulation), scenario switcher (`routine`, `impersonation`, `verified`, `unavailable`, `agent`), drawer inspection panels, and audit event logs.
  - Connected the frontend to the new FastAPI backend health probes (`/health/ready` and `/health/live`) without modifying the core user journeys or rewriting the UI from scratch.
  - Excluded Replit-specific plugins, Express api-server stubs, and Drizzle artifacts.

## 2. Repository Conventions

- **Paths**:
  - `backend/app/`: Application source code.
  - `backend/tests/`: Unit and integration test suites.
  - `frontend/src/`: React source code.
  - `docs/project/`: Persistent project governance documents (`prd.md`, `architecture.md`, `rules.md`, `task.md`, `memory.md`).
- **Configuration**:
  - Backend reads `.env` via `app.core.config.Settings`.
  - Frontend reads `VITE_API_BASE_URL` from Vite env vars.
  - Secrets are never committed; safe defaults in `.env.example`.
- **Health Check Conventions**:
  - `GET /health/live`: Fast process liveness check (HTTP 200, no external dependencies).
  - `GET /health/ready`: Database dependency readiness check (`SELECT 1`). Returns HTTP 200 on success, HTTP 503 on failure.

## 4. Confirmed Decisions & Architectural Patterns

- **Task-Tracker Realignment**: In accordance with user requirements, the Deterministic Risk Engine belongs to Phase 1, and the AI Investigation Agent belongs to Phase 2.
- **State Machine Architecture**: Authoritative 10-state workflow lifecycle implemented in `app.domain.state_machine`. Pure domain logic with `validate_transition`, `can_transition`, and `is_terminal`.
- **Deterministic Risk Engine Principles**:
  - Feature evaluation from concrete transaction and evidence inputs only (zero ML / LLM in Phase 1).
  - No scenario IDs, scenario names, or keyword shortcuts in scoring logic.
  - Missing evidence is explicitly captured as unknown, never silently assumed safe or dangerous.
  - Relative risk score (0–100), risk levels (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), and policy recommendations (`ALLOW`, `WARN_CUSTOMER`, `REQUIRE_VERIFICATION`, `HOLD_FOR_INVESTIGATION`, `BLOCK_SIMULATED`).
  - Core guardrail: Trusted recipient status CANNOT override strong coercion indicators. Voice stress alone is NOT proof of fraud.
- **AI Investigation Architecture & Boundaries (Phase 2)**:
  - **Primacy of Deterministic Policies**: The LLM investigates evidence and produces intelligence; it **never** mutates transaction state or bypasses the deterministic state machine.
  - **Evidence Integrity & Provenance Grounding**: Every finding cites concrete evidence references validated against supplied inputs (`stmt_*`, `doc_*`, telephony telemetry, recipient flags, triggered rules). Fabricated/unknown references are rejected and tracked in `missing_information`. Findings with empty or ungrounded evidence references default to `EvidenceProvenance.MODEL_INFERENCE`.
  - **Prompt Injection Defense & Non-Malice Invariant**: Customer statements and document text are treated as untrusted data inside explicit forensic tags (`<untrusted_customer_statements>`, `<untrusted_extracted_documents>`), never as instructions. Adversarial overrides are detected and flagged under `FindingCategory.SOCIAL_ENGINEERING`. Prompt injection in untrusted customer text is treated as manipulation, NEVER as proof of customer malice (`MALICIOUS`).
  - **Multi-Turn Investigation Dialogue Invariants (P2-A2)**:
    - Bounded to `INVESTIGATION_MAX_CONVERSATION_TURNS = 20`. Exceeding limit raises HTTP 400 `ConversationTurnLimitError`.
    - Strict cross-transaction isolation: any access or turn addition to a conversation associated with a mismatched transaction ID immediately yields HTTP 404 `RESOURCE_NOT_FOUND`.
    - Transaction State & Audit Invariance: Conversation initialization and turn submissions execute inside independent transactional boundaries without altering transaction `state`, `version`, or appending to `transaction_audits`.
    - Contextual Memory & Anti-Repetition: Assistant turns analyze complete prior turn history and generate distinct, decision-relevant follow-up prompts that omit inquiries already resolved.
    - Idempotency & Concurrency: Client turns support optional `client_turn_id` idempotency token (enforced since the 2026-10-17 audit via a replay check in `submit_conversation_turn`: a repeated token returns current state instead of appending duplicate turns); conversation updates verify optimistic locking version increment. Turn ordering is protected at the DB level by `uq_conversation_turn_index` (unique on `conversation_id, turn_index`), which also bounds the 20-turn limit under concurrent inserts.
    - Prompt History Fidelity (audit lesson): conversation-history dicts passed to `build_conversation_investigation_prompt` MUST use keys `turn_index` and `evidence_provenance` (the builder reads those). A prior key mismatch (`provenance`, no `turn_index`) rendered every historical turn as `index="0" provenance="none"` — content was still passed, only labels were wrong.
  - **Provider Selection & Credential Transparency**: Controlled via `AI_PROVIDER` setting (`auto`, `vertex_ai`, `gemini_api`, `mock`). Metadata explicitly reports `"mock_gemini"` vs `"vertex_ai"`; mock outputs are never misrepresented as live AI findings. Missing credentials on live providers raise HTTP 503 `AI_CONFIGURATION_ERROR`.
  - **Authentication & Authorization (P2-A2.1, implemented)**: Operations-console routes require an authenticated **operator** via `get_current_operator` ([ADR-002](../decisions/ADR-002-operator-authentication.md)). Login (`POST /api/v1/auth/login`) validates a bcrypt hash in the `operators` table (migration `0006`) and issues a short-lived HS256 **Bearer JWT** (`AUTH_JWT_SECRET`, fail-closed). Authorization model is **operator-shared** (any active operator may access any case, matching the bank-wide console persona); transaction-scoped conversation routes also enforce `conversation.transaction_id == transaction_id`. `/auth/login` and `/health/*` are public. Demo login is provisioned on startup from `AUTH_BOOTSTRAP_OPERATOR_USERNAME`/`_PASSWORD` (idempotent). Libraries: `PyJWT`, `bcrypt` (no custom crypto). Frontend gates the console behind an `AuthGate` login screen and sends the token via a shared `apiFetch` wrapper that forces logout on 401.
  - **Former blocker (now resolved for the operator model)**: the prior "no authentication / IDOR" deployment blocker from the P2-A2 audit is closed. Remaining future work (not blockers for a private demo): per-operator audit attribution, role tiers, token revocation/refresh, `/auth/login` rate limiting, external IdP for production multi-tenant use.
  - **Auth hardening (security review of `777fae8`)**: JWT decode now *requires* `exp` and `sub` (a token lacking `exp` is rejected, not treated as non-expiring); algorithm allowlist already rejects `alg=none` and HS512/HS256 confusion. Login uses a real bcrypt hash for the unknown-user path so timing does not reveal account existence (response text was already identical). Durable rule: when adding a timing-equalization fallback, the fallback hash MUST be a valid bcrypt hash or `verify_password` short-circuits and the defense is void. **Not public-production ready**: `/auth/login` still has no rate limiting/lockout; HTTPS/TLS and per-environment `CORS_ORIGINS` + strong `AUTH_JWT_SECRET` are deployment requirements.
  - **Customer Verification Lifecycle Architecture (P2-A5, ADR-004)**:
    - Dedicated `verification_challenges` entity (migration `0008`) bound to transaction and customer.
    - Zero plaintext OTP storage: stores HMAC-SHA256 keyed digest (`hash_otp`) compared via constant-time comparison (`verify_otp`).
    - Identity Separation: Submissions require a distinct, short-lived customer verification session token (`type="customer_verification"`); an operator bearer token cannot submit challenges, preventing false attribution.
    - Path and Token Binding: The session token explicitly binds `challenge_id`, `transaction_id`, and `customer_id`. Submitting across transactions or challenges yields HTTP 404.
    - Single-Use & Concurrency Safety: Optimistic locking on challenge `version` ensures only one concurrent request consumes a challenge; second attempts or replays return the existing resolved decision idempotently without re-transitioning.
    - Policy Re-Evaluation Boundary: Verification success satisfies `REQUIRE_VERIFICATION` to `ALLOW` (simulated settlement) only when residual risk is acceptable. Strong residual fraud indicators (e.g. duress/coercion, confirmed mule registry) remain held/blocked (`HOLD_FOR_INVESTIGATION` / `BLOCK`). Verification failure or attempt exhaustion immediately escalates to `HOLD_FOR_INVESTIGATION` and never authorizes settlement.
    - Simulation Boundary: Clearly labeled in frontend UI and API schemas as a simulated mechanism; dev-only OTP exposure (`dev_otp`) is strictly controlled by `VERIFICATION_EXPOSE_DEV_OTP` and nullified in production.
  - **Verification Concurrency Hardening & Abuse Defense (P2-A5.1, ADR-004 amendment)**:
    - **ORM Attribute Access Post-Rollback (`MissingGreenlet` prevention)**: In SQLAlchemy async sessions, rollback or update expiration invalidates ORM instance attributes in the identity map. Accessing attributes on expired instances outside greenlet context triggers `MissingGreenlet`. Pre-cache required scalar values (`cid`, `customer_id`, `version`, `attempt_count`) prior to database mutations, and re-query fresh models using awaited repository calls.
    - **Two-Phase Status Progression Gap**: The transition sequence `PENDING` -> `VERIFIED` -> `CONSUMED` created a transient gap where concurrent requests observed `status="VERIFIED"` before `decision_id` was committed. Fixed via bounded in-flight polling (up to 3.0s in 100ms intervals), ensuring success is never reported before decision persistence. An optimistic claim retry loop (up to 3 attempts) in `_handle_correct` prevents spurious failures during concurrent attempt count increments.
    - **Partial Unique Index for Active Challenges**: Enforced single pending challenge per transaction using PostgreSQL partial unique index `uq_verification_challenges_pending_tx` (`WHERE status = 'PENDING'`). This allows multiple historical challenges (`EXPIRED`, `CONSUMED`, `FAILED`, `SUPERSEDED`) without violating uniqueness.
    - **State Machine Guarding & Partial Failure Recovery**: Challenge submission validates `tx.state == VERIFICATION_REQUIRED`, rejecting terminal transactions (`TRANSACTION_TERMINAL`, 409) and non-required states (`VERIFICATION_NOT_REQUIRED`, 409). Partial failure recovery sets `status="FAILED"`, `failure_reason="RESOLUTION_FAILED"` if workflow resolution fails, preventing stranded challenges with `decision_id=None`.
    - **Key Decoupling & Dual-Key Rotation**: Separated `VERIFICATION_HMAC_SECRET` from `AUTH_JWT_SECRET`. `verify_otp` supports dual-key fallback (checks primary secret first, falls back to legacy/secondary secret), enabling zero-downtime key rotation for in-flight challenges.
    - **Database-Backed Rate Limiting**: Added `count_recent_challenges_for_transaction` to enforce bounded challenge creation per window (HTTP 429 `RATE_LIMIT_EXCEEDED`).
  - **Voice Duress & Coercion Intelligence Architecture (P2-A6, ADR-005)**:
    - **Deterministic Primacy & Separation of Concerns**: Coercion analysis provides qualitative forensic intelligence and structured findings; the deterministic policy engine retains exclusive authority over transaction actions and state transitions. The model never dictates transaction state.
    - **Verbatim Grounding Invariant**: Every citation in a coercion finding must match verbatim a substring of the supplied transcript via programmatic validation (`validate_transcript_excerpt`). Hallucinated, imprecise, or ungrounded citations are stripped from findings and recorded in `uncertainty_notes`.
    - **Prompt Injection Defense & Non-Malice Invariant**: Simulated phone call transcripts are isolated within `<untrusted_simulated_call_transcript>` XML tags. Malicious prompt injection directives embedded in transcripts (e.g., instructions to ignore rules or approve transactions) are classified under `SAFEGUARD_BYPASS_INSTRUCTION` and treated as social engineering manipulation against the customer, never as customer malice.
    - **Acoustic Telemetry Advisory Boundary**: Voice stress signals (`voice_stress_score`, `voice_stress_level`) are acoustic telemetry from simulated calls. They are strictly non-disqualifying (`VOICE_STRESS_ALONE_NON_DISQUALIFYING`) and can NEVER independently cause a transaction hold, block, or fraud determination.
    - **Coercion Guardrail on Verification**: Explicit CRITICAL or HIGH coercion findings escalate policy action to `HOLD_FOR_INVESTIGATION` (`EXPLICIT_COERCION_HOLD`). A successful customer OTP verification CANNOT clear explicit coercion (`VERIFICATION_INSUFFICIENT_RESIDUAL_RISK`), protecting victims under active coercive pressure from unknowingly authorizing fraudulent transfers.
    - **Safe Degraded Mode & Idempotent Deduplication**: AI provider timeouts or upstream failures degrade gracefully to `status="UNAVAILABLE"`, allowing deterministic policy workflows to proceed without unhandled errors. Repeated submissions of identical transcripts return existing persisted analyses without redundant model calls.
  - **Automated Fraud Response & Customer Intervention Architecture (P2-A7, ADR-006)**:
    - **Automated Lifecycle Orchestration**: Connects deterministic decisions to simulated transaction states (`ALLOW_SETTLED`, `VERIFICATION_REQUIRED`, `HOLD_PROTECTIVE`, `BLOCK_SAFETY`) and customer communication autonomously without mandatory operator intervention.
    - **Customer Intervention Safety**: Headlines and messages are empathetic, non-accusatory, and easy to understand. Explicitly warns against calling numbers provided by suspicious callers and directs solely to official bank contact methods (e.g. number on the back of card). Never exposes internal rule IDs (`RULE_FLAGGED_MULE_ACCOUNT`) or mule consortium vocabulary.
    - **Notification Delivery Failure Isolation**: Simulated network/carrier timeouts (`FAILED_SIMULATED`, `SIMULATED_CARRIER_TIMEOUT`) are recorded in notification logs but strictly isolated from policy safety decisions: delivery failures can never silently reverse, downgrade, or release a hold or block.
    - **Credential & Telemetry Redaction**: Notification recipients are masked (`p***a@upi`). Notification bodies are sanitized to guarantee zero OTPs, bearer tokens, passwords, or sensitive transcripts appear in notification records or server logs.
    - **Idempotency & Concurrency Hardening**: Scoped per `(transaction_id, idempotency_key)` backed by PostgreSQL unique constraint. Rollback paths in `ResponseOrchestrationService` explicitly re-query scalar IDs rather than accessing expired ORM attributes to prevent `MissingGreenlet` errors.
  - **Confidence Calibration**: Qualitative confidence score (0.0 to 1.0) reflects model assessment certainty, not calibrated statistical fraud probability.
- **Idempotency Strategy**: Scoped per `(customer_id, idempotency_key)` backed by PostgreSQL unique constraint and canonical SHA-256 payload hash.
- **Concurrency Control**: Optimistic version locking via integer `version` incremented on each state change.
- **Audit Integrity**: Append-only `transaction_audits` recorded atomically in the same database transaction.
- **Risk Assessment History**: Persisted in `transaction_assessments` table, retaining complete input snapshot, triggered rules, supporting evidence, and missing evidence.
- **Investigation History**: Persisted in `transaction_investigations` table, linked to transactions and optional deterministic assessments (`ondelete="SET NULL"`).
- **Conversation History**: Persisted in `investigation_conversations` and `investigation_conversation_turns` tables with foreign keys and cascaded lifecycle.
- **Verification History**: Persisted in `verification_challenges` table with foreign keys to transactions and transaction decisions.
- **Coercion History**: Persisted in `transaction_coercion_analyses` table with foreign keys to transactions and optional deterministic assessments.
- **Response & Notification History**: Persisted in `transaction_responses` and `transaction_notifications` tables with foreign keys and unique constraints.
- **Scenario Run History**: Persisted in `scenario_runs` table (migration `0012`) with a unique `idempotency_key`, an `execution_mode`, a nullable `transaction_id` FK, and an ordered JSON `stages` timeline that references authoritative records by id (no duplication of transcripts/OTPs/tokens). `status` reports workflow-execution progress, which is deliberately separate from fraud-decision correctness (evaluated on demand from live persisted artifacts).
- **Call Session History**: Persisted in `transaction_call_sessions` table (migration `0013`) with foreign key to transactions, optimistic locking, and linked `investigation_conversations` (`conversation_type="customer_dialogue"`).
- **Call Session Reliability (P2-A10 audit)**:
  - **One active session per transaction** is enforced by a PostgreSQL partial unique index `uq_call_sessions_active_tx` (`status IN ('INITIATED','RINGING','CONNECTED')`), not just a read-before-write guard; initiation creates the session first and resolves a losing race by returning the winner.
  - **Recoverable init failure**: if the opening Gemini turn fails, the session is marked terminal `FAILED` (not left active) and its conversation closed, so retries start clean.
  - **Terminal states are immutable**: `complete` is idempotent on `COMPLETED` but refuses to overwrite any other terminal state (`DECLINED`/`TIMED_OUT`/`FAILED`/`CANCELLED`) — no silent audit rewrites.
  - **Turn-index races** rely on the existing `(conversation_id, turn_index)` unique constraint; repositories roll back and re-raise `IntegrityError`, and `submit_turn` maps it to HTTP 409.
  - **Coercion policy** runs from the *accumulated* transcript (all turns) on both automatic and manual completion via one shared helper; its failure is logged-and-swallowed and never mutates transaction state (deterministic policy stays authoritative; voice stress stays advisory).
  - **Authorization**: customer verification tokens are scoped to their bound `transaction_id` (prevents cross-transaction IDOR; `AuthorizationError`→403), and internal forensic fields (observations, uncertainty, suggested action, coercion cues, risk sentiment, evidence refs) are redacted from customer responses — returned only to operators.
  - **`TIMED_OUT` is reserved**: no server-side timeout sweeper exists; dialogues are bounded by `MAX_DIALOGUE_TURNS` and client-driven decline/complete.
  - **Frontend idempotency**: `App.tsx` sends a per-answer `client_turn_id` and guards against re-entrant turn submissions.
- **Real-Time Live Voice (P2-A11)**: Bidirectional Gemini Live audio over an authenticated WebSocket `WS /api/v1/calls/{id}/live`.
  - **SDK**: `google-genai` 2.31.0 Live API (`client.aio.live.connect`, `LiveConnectConfig` with `response_modalities=["AUDIO"]`, input/output `AudioTranscriptionConfig`, `SpeechConfig` voice, `SessionResumptionConfig`, `ContextWindowCompressionConfig`). Model/voice are env-configurable (`GEMINI_LIVE_MODEL`, default `gemini-2.0-flash-live-001`; `GEMINI_LIVE_VOICE`), never hardcoded in logic. Audio: 16 kHz PCM16 in, 24 kHz PCM16 out.
  - **Provider abstraction**: `LiveVoiceClient`/`LiveVoiceSession` with a real `GeminiLiveVoiceClient` and a deterministic `MockLiveVoiceClient`; the Gemini key stays server-side and is read from settings — never sent to the browser.
  - **Orchestrator** (`live_voice_service.py`): bounded queues + independent ingest/egress/persistence/analysis/watchdog tasks; audio forwarding/playback is never blocked by DB or analysis; a single persistence writer assigns monotonic `seq` and dedups; transcript queue applies a bounded (0.1 s) backpressure-then-drop policy. All tasks are cancelled/drained and the provider session closed on termination; `finalize` flushes trailing text and runs a final analysis or marks it incomplete.
  - **Persistence**: `call_transcript_segments` (migration `0014`, unique `(call_session_id, seq)`, only final/corrected persisted; interim partials stream to UI only) and `call_live_analyses` (versioned `live-analysis-v1` snapshots; latest by `created_at` is current, older superseded).
  - **Analysis**: `LiveEvidenceAnalyzer` is grounded (findings cite transcript `seq` refs), incremental, non-overlapping, advisory only; it never changes transaction/call state. Escalation to COERCED requires ≥2 combined coercion markers; voice tone is never an input. Failure degrades to status `unavailable` without interrupting voice.
  - **Security**: WS authenticated (operator JWT or customer token) and transaction-scoped (no cross-transaction streams); frame-size/queue/session-duration/concurrency caps; one live session per call; Live-disabled gate closes the socket (browser then uses text fallback). Internal analysis is operator-only. `GEMINI_LIVE_ENABLED` without credentials fails config validation at startup.
  - **Frontend**: `liveVoiceClient.ts` (capability detection, resample, WS, incremental playback, barge-in, cleanup, explicit non-silent fallback) + `public/audio/pcm-capture-worklet.js`. `App.tsx` attempts Live only when audio capture is supported, so jsdom tests and unsupported browsers keep the existing simulated path.
  - **Verification**: real Gemini Live path is MOCK-VERIFIED ONLY here; `tests/integration/test_live_voice_smoke.py` runs the real handshake only with `GEMINI_LIVE_SMOKE=1` + credentials. The earlier chat-pasted API key is considered compromised — revoke/replace, never reuse.
- **Transaction Intelligence, Selective Calls & Gemini Config (P2-A12)**:
  - **Gemini Settings & Environment Sanitization**: `backend/app/core/config.py` canonical `.env` resolution across root and backend working directories. Strips quotes/whitespace and checks `GOOGLE_API_KEY`/`AI_STUDIO_API_KEY`. Dynamic `Settings()` instantiations prevent stale singletons from causing false `503 AI_CONFIGURATION_ERROR`. Exposed keys in chats are flagged compromised.
  - **Decoupled Call Session Lifecycle**: When `GEMINI_LIVE_ENABLED=True` and channel is simulated voice, call creation transitions directly to `RINGING` without an unnecessary synchronous text-generation call. The Live WebSocket streams the dynamic opening turn. Scalar attributes cached upfront to eliminate `MissingGreenlet` errors.
  - **Fictional Recipient Registry (Migration 0015)**: Database-backed registry of 20 deterministic demonstration identities (8 trusted, 5 unknown, 7 high-risk: mules, fast fan-in/fan-out, authority impersonation, high-yield schemes). Seeded idempotently during startup and test runs.
  - **Server-Controlled Risk Evidence**: `RiskService.assess_transaction` resolves `recipient_identifier` against the database registry; authoritative server records override client-supplied mock flags (`is_trusted_beneficiary`, `is_flagged_mule`, `fan_in_count_24h`, `fan_out_count_24h`).
  - **Selective Bank-Initiated Calls**: Unconditional frontend call creation removed. `App.tsx` submits payment and awaits automated workflow evaluation; only when policy decision is `REQUIRE_VERIFICATION` does the bank ring. Customer-scoped tokens are explicitly forbidden (`403 FORBIDDEN`) from calling `POST /api/v1/transactions/{id}/calls` directly.
